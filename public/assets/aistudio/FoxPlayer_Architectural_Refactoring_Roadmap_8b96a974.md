# FoxPlayer — خطة إعادة الهيكلة المعمارية والتطوير المستدام

**نوع المستند:** خطة تنفيذ مرحلية  
**المشروع:** FoxPlayer — Android / Kotlin / Jetpack Compose  
**الهدف الرئيسي:** إعادة تنظيم المعمارية والكود تدريجيًا مع الحفاظ على كل المميزات الحالية وسلوك التطبيق، ثم استكمال التطوير على أساس قابل للصيانة والاختبار.

---

## 1. الرؤية والهدف

المطلوب ليس تقليل عدد الأسطر بأي ثمن، ولا تقسيم كل ملف إلى ملفات صغيرة عشوائيًا. المطلوب أن تكون مسؤوليات الكود وحدوده واضحة، وأن يمكن تعديل ميزة دون الحاجة إلى فهم التطبيق كله أو المخاطرة بكسر أجزاء غير مرتبطة بها.

### النتائج المستهدفة

- الحفاظ على كل الميزات الحالية وتجربة المستخدم وسلوك التشغيل.
- تقليل تركز المنطق في الملفات والشاشات الكبيرة.
- فصل واجهة المستخدم عن منطق الأعمال والتشغيل والتخزين.
- توضيح اتجاه الاعتماد بين الطبقات ومنع الاعتماديات الدائرية.
- تحسين الاختبارات بحيث تكشف الانحدارات مبكرًا.
- تسهيل عمل المطورين ووكلاء الذكاء الاصطناعي على تغييرات محدودة.
- استكمال الميزات المستقبلية دون إضافة تعقيد معماري غير ضروري.

### ما لا تهدف إليه الخطة

- إعادة كتابة التطبيق من الصفر.
- تغيير تصميم التطبيق أو تجربة المستخدم أثناء إعادة الهيكلة.
- إنشاء Gradle modules كثيرة قبل إثبات الحاجة إليها.
- نقل الكود لمجرد تقليل عدد الأسطر.
- تغيير سلوك التطبيق أو حذف ميزة باعتبار ذلك «تنظيفًا».
- اعتبار نجاح اختبارات JVM دليلًا على أن كل حالات Android الفعلية سليمة.

## 2. مبادئ التنفيذ غير القابلة للتفاوض

1. **الحفاظ على السلوك:** إعادة الهيكلة تغيّر التنظيم الداخلي، لا السلوك المرئي للمستخدم، إلا عند اعتماد إصلاح محدد بصورة صريحة.
2. **التدرج:** تغيير نطاق واحد في كل مرحلة، وعدم تنفيذ إعادة كتابة ضخمة دفعة واحدة.
3. **خط أساس واضح:** تسجيل commit البداية، وحالة الاختبارات، وحالة Git قبل التعديل.
4. **عدم خلط المهام:** لا تُضاف ميزات جديدة أثناء مراحل إعادة الهيكلة إلا إذا كانت ضرورية لإصلاح عطل أو اجتياز الاختبارات، مع توثيق السبب.
5. **اختبارات قبل النقل وبعده:** تُضاف اختبارات السلوك المفقودة قبل إعادة تنظيم المنطق عالي المخاطر.
6. **لا حذف بلا دليل:** لا يُحذف كود أو مورد إلا بعد التأكد من عدم استخدامه وعدم تأثيره على السلوك أو التوافق.
7. **حدود واضحة للمسؤولية:** كل مكون يملك مسؤولية مفهومة، وواجهات تعامل محددة مع المكونات الأخرى.
8. **لا تقسيم شكلي:** لا يُفرض حد ثابت لعدد الأسطر. المعيار هو الترابط الداخلي، وحجم المسؤولية، وقابلية الاختبار والفهم.
9. **لا اعتماد دائري:** يجب أن تكون علاقات الحزم والطبقات واضحة وغير دائرية.
10. **تغييرات قابلة للمراجعة والرجوع:** يجب أن يكون كل جزء صغيرًا بما يكفي لفهمه ومراجعته وإعادة تطبيقه أو التراجع عنه.
11. **توثيق الأدلة:** يجب التمييز بين اختبار نجح فعلًا، واختبار تعذّر تشغيله بسبب البيئة، واختبار لم يُنفذ.
12. **لا نشر دون إذن:** لا يتم commit أو push إلا وفق الإذن الصريح ونطاق المهمة المحدد.

## 3. صورة المعمارية المستهدفة

هذه صورة مفاهيمية وليست أمرًا بإنشاء كل الحزم المقترحة حرفيًا. يجب تدقيق المستودع أولًا، ثم تكييف الأسماء والبنية وفق الكود الفعلي.

```text
app/
├── app-entry/
│   └── Application / Activity / navigation setup
├── ui/
│   ├── library/
│   │   ├── screen/
│   │   ├── components/
│   │   └── state/
│   ├── player/
│   │   ├── screen/
│   │   ├── components/
│   │   ├── gestures/
│   │   └── state/
│   ├── settings/
│   └── shared/
├── domain/
│   ├── model/
│   ├── repository/
│   └── usecase/              # عند وجود منطق يستحق الفصل
├── data/
│   ├── repository/
│   ├── local/
│   ├── database/
│   └── preferences/
├── core/
│   ├── playback/
│   ├── media/
│   ├── common/
│   └── platform/
└── tests/
    ├── unit tests
    ├── integration tests
    └── UI / instrumentation tests
```

### اتجاه الاعتماد المقترح

- `ui` يعرض الحالة ويرسل نوايا المستخدم إلى منطق التطبيق.
- `domain` يحتوي نماذج وقواعد أعمال مستقلة عن واجهة Android قدر الإمكان.
- `data` ينفذ الوصول إلى البيانات والتخزين ويوفر العقود المطلوبة.
- `core/playback` يدير تكامل التشغيل مع Android وMedia3 وفق الحدود الموجودة بالمشروع.
- لا ينبغي أن يعتمد `domain` على `ui`.
- لا ينبغي أن تتعامل عناصر الواجهة مباشرة مع تفاصيل قاعدة البيانات أو تنفيذ التخزين.
- لا تُنشأ طبقة أو واجهة تجريدية إلا إذا كانت تحل اقترانًا فعليًا أو تسهّل الاختبار والتغيير.

قد تظل كل هذه الحزم داخل Gradle module واحد في البداية. قرار تقسيم Gradle modules مؤجل إلى أن تظهر حاجة مثبتة مثل استقلال الاختبارات أو ملكية واضحة أو تقليل زمن البناء أو فرض حدود اعتماد لا يمكن ضمانها بالحزم وحدها.

## 4. خريطة المسؤوليات

| الجزء | المسؤولية الأساسية | ما يجب تجنبه |
|---|---|---|
| `PlayerScreen` | تركيب واجهة المشغل وربط الحالة والأحداث | احتواء كل منطق التشغيل والإيماءات والتخزين |
| مكونات Player UI | عرض عناصر التحكم والحالة المرئية | امتلاك دورة حياة الخدمة أو المستودعات |
| Gestures | تفسير اللمس والنقر والسحب وتحويلها إلى أحداث | تغيير حالة التشغيل من مسارات متفرقة وغير موحدة |
| `PlaybackService` | خدمة التشغيل وتكامل Android وMediaSession والإشعارات حسب التصميم الحالي | أن تصبح مكانًا لكل قواعد التطبيق |
| `ActivePlaybackSource` | مصدر موحد للحالة النشطة وفق عقد واضح | ازدواجية مصادر الحالة أو الاعتماد على توقيتات اعتباطية |
| Controller lifecycle | إنشاء/ربط/فصل/تحرير controller بطريقة آمنة | delays أو polling لإخفاء أخطاء دورة الحياة |
| مستودعات البيانات | قراءة وكتابة البيانات وإخفاء تفاصيل التخزين | منطق واجهة المستخدم |
| Settings repository | حفظ الإعدادات وإرجاع تدفق واضح للقيم | تخزين التفضيلات في متغيرات متفرقة داخل الشاشات |
| Thumbnail handling | تنظيم استخراج الصور المصغرة والتخزين المؤقت إن كان ضمن المشروع | عمليات ثقيلة أو متكررة داخل تركيب الواجهة |
| Library features | قواعد المفضلة وقوائم التشغيل والمجلدات | الاعتماد المباشر على تفاصيل شاشة المشغل |

الأسماء المذكورة ليست إلزامية؛ يجب التأكد من وجود المسؤولية فعلًا قبل إنشاء ملف أو حزمة جديدة.

# 5. خطة التنفيذ المرحلية

## المرحلة 0 — تثبيت نقطة البداية وخط الأساس

### الهدف
تحديد النسخة التي ستُجرى عليها إعادة الهيكلة، وفهم حالة المشروع قبل لمس الكود.

### المهام
- التحقق من المستودع والفرع والـ commit الحالي.
- فحص `git status` وتسجيل كل التعديلات والملفات غير المتتبعة.
- عدم حذف أو استبدال أي تغييرات موجودة دون معرفة مالكها وسببها.
- تسجيل إصدار Kotlin وGradle وAndroid Gradle Plugin وMedia3 وأهم الاعتماديات.
- تشغيل الاختبارات المتاحة وLint والاختبارات البصرية عند توفر متطلباتها.
- تسجيل الاختبارات التي فشلت مسبقًا، والتحذيرات، والقيود البيئية.
- تحديد تعليمات البناء والتشغيل الفعلية من ملفات المشروع.

### المخرجات
- تقرير خط أساس.
- SHA واضح للنسخة المرجعية.
- قائمة بالتغييرات الموجودة قبل البدء.
- نتائج الاختبارات مع الأوامر الفعلية والمخرجات.

### بوابة النجاح
يمكن إعادة إنتاج حالة البناء والاختبارات، أو توجد قائمة صريحة بالمشكلات السابقة والقيود التي تمنع ذلك.

## المرحلة 1 — تدقيق معماري ورسم خريطة الاعتماديات

### الهدف
تحديد أماكن التركز والاقتران قبل اتخاذ قرارات النقل.

### المهام
- حصر أكبر الملفات وأعلى الملفات مسؤوليةً وتشابكًا.
- تتبع مسار تشغيل الفيديو من الواجهة إلى الخدمة ومحرك التشغيل.
- تتبع تدفق حالة التشغيل من مصدرها إلى عناصر الواجهة.
- تتبع دورة حياة Activity وService وMediaController وسطح الفيديو.
- مراجعة المكتبة والمفضلة وسجل المشاهدة واستكمال التشغيل والإعدادات.
- رسم الاعتماديات بين `ui` و`core` و`data` وأي طبقات موجودة بالفعل.
- تحديد الاعتماديات الدائرية والوصول المباشر إلى التخزين أو Android APIs من أماكن غير مناسبة.
- تحديد التكرار الحقيقي في الكود، مع عدم اعتبار كل تشابه تكرارًا يستحق التجريد.
- رصد الملفات التي يصعب اختبارها وأسباب ذلك.

### المخرجات
- خريطة تدفق تشغيل الفيديو.
- خريطة تدفق البيانات والإعدادات.
- قائمة بالمشكلات المعمارية مرتبة حسب المخاطر والأثر.
- اقتراح ترتيب النقل مع مبرر لكل تغيير.

### بوابة النجاح
لا يبدأ النقل واسع النطاق قبل توثيق ما الذي سيتغير، وما الذي يجب أن يظل ثابتًا، وكيف سيُختبر كل جزء.

---

## المرحلة 2 — حماية السلوك الحالي بالاختبارات

### الهدف
إنشاء شبكة أمان قبل تحريك المنطق بين الملفات.

### المهام
- الاحتفاظ باختبارات Snackbar الحالية وسلوك الفشل وإعادة تركيب الواجهة وتدمير Activity.
- الحفاظ على اختبارات `ActivePlaybackSource` و`ControllerLifecycle` و`PlayerScreenPlaybackSource` الموجودة.
- إضافة اختبارات للسلوك المهم غير المغطى، وفق نتائج التدقيق.
- اختبار الحالات الحدّية لتدفق حالة التشغيل والاتصال والفصل وتغيير المصدر.
- فصل اختبارات منطق Kotlin عن الاختبارات التي تحتاج Android runtime أو جهازًا.
- عدم استخدام الاختبارات الهشة المعتمدة على توقيتات أو sleeps إلا إذا كان ذلك لا مفر منه ومبررًا.
- إضافة اختبارات تكامل عند الحاجة للتحقق من حدود المكونات.
- توثيق الحالات التي لا يمكن إثباتها إلا على جهاز حقيقي.

### المخرجات
- قائمة اختبارات حماية للسلوك.
- اختبارات جديدة محددة بالمخاطر المكتشفة.
- تقرير بالفجوات المتبقية في التغطية.

### بوابة النجاح
الاختبارات الحرجة تمر قبل النقل، أو تكون حالات الفشل السابقة موثقة ومفصولة عن الانحدارات الجديدة.

## المرحلة 3 — تفكيك `PlayerScreen` دون تغيير السلوك

### الهدف
تقليل مسؤوليات شاشة المشغل وجعل تعديل مكوناتها مستقلًا نسبيًا.

### المهام
- تحليل `PlayerScreen` إلى مجموعات مسؤوليات فعلية.
- فصل مكونات الواجهة القابلة لإعادة الاستخدام عن تنسيق الشاشة.
- نقل منطق الإيماءات إلى مكون أو منسق مستقل عند الحاجة.
- فصل تنسيق الحالة والأحداث عن العرض المرئي، دون إدخال ViewModel لمجرد اتباع نمط شائع.
- توحيد تمثيل الأحداث ذات الصلة بالتشغيل بدل وجود مسارات متفرقة ومتضاربة.
- إبقاء النصوص والتنسيقات والتصميم وسلوك عناصر التحكم كما هي.
- منع المكونات الفرعية من إنشاء Controllers أو خدمات تشغيل بشكل مستقل إذا كان ذلك يخالف ملكية دورة الحياة.
- تحديث الاختبارات مع كل خطوة نقل.
- مراجعة API الداخلية للمكونات لتقليل عدد الاعتماديات التي تحتاجها.

### المخرجات
- شاشة رئيسية مسؤولة عن التركيب والتنسيق.
- مكونات مستقلة ذات أسماء ومسؤوليات واضحة.
- اختبارات تثبت الحفاظ على السلوك الأساسي.

### بوابة النجاح
- لا توجد تغييرات غير مقصودة في الواجهة أو سلوك التشغيل.
- الاختبارات ذات الصلة تمر.
- لا يتم تمرير كميات كبيرة من الحالات والأحداث بلا داعٍ بين المكونات.

---

## المرحلة 4 — تثبيت حدود طبقة التشغيل ودورة الحياة

### الهدف
جعل مصدر حالة التشغيل ودورة حياة MediaController وسطح الفيديو مفهومة وقابلة للاختبار.

### المهام
- مراجعة العلاقة بين `PlaybackService` و`ActivePlaybackSource` و`ControllerLifecycle` والواجهة.
- التأكد من وضوح الجهة المالكة لكل Player وController وSurface.
- توحيد التعامل مع الاتصال والانقطاع وإعادة الاتصال وتدمير الخدمة.
- مراجعة أوامر MediaSession المتاحة للـ Controller وفق إصدار Media3 المستخدم والعقد الرسمي.
- التأكد من أن أوامر الوصول إلى العنصر الحالي أو ربط سطح الفيديو مسموحة عندما يتطلبها التصميم الفعلي.
- مراجعة فصل السطح وإعادة ربطه أثناء إعادة إنشاء Activity.
- مراجعة حالات تغيير مصدر الفيديو واستبدال Player وانتهاء الجلسة.
- عدم إدخال تأخيرات أو polling أو مسارات fallback إضافية إلا لسبب موثق.
- إضافة اختبارات حتمية قدر الإمكان للحالات التي يمكن اختبارها في JVM.
- تنفيذ اختبارات على جهاز أو Emulator لحالات Surface ودورة الحياة التي لا يمكن إثباتها باختبارات الوحدة وحدها.

### المخرجات
- حدود واضحة بين الواجهة والخدمة ومصدر الحالة.
- اختبارات للحالات الحرجة.
- قائمة صريحة بما تم اختباره على JVM وما تم اختباره على جهاز.

### بوابة النجاح
لا يوجد خلل معروف في دورة الحياة، ولا يُدّعى أن اختبارًا وحدويًا يثبت استمرارية Surface أو PiP على جهاز حقيقي.

---

## المرحلة 5 — فصل منطق البيانات والتخزين

### الهدف
منع الشاشات والميزات من الوصول المباشر وغير المنظم إلى تفاصيل التخزين.

### المهام
- جرد مصادر البيانات الحالية، مثل قاعدة البيانات والملفات وSharedPreferences أو DataStore وفق الموجود فعلًا.
- تحديد مصدر الحقيقة لكل نوع بيانات.
- تنظيم مستودعات البيانات حول مجالات واضحة.
- فصل نماذج التخزين عن نماذج المجال إذا كان الاختلاف له قيمة عملية.
- جعل تدفقات البيانات وتحديثاتها واضحة وقابلة للاختبار.
- معالجة حالات فشل القراءة والكتابة وعدم توفر الملفات.
- منع منطق قاعدة البيانات من التسرب إلى عناصر Compose.
- الحفاظ على توافق البيانات الحالية وعدم تغيير المخطط أو ترحيل البيانات إلا ضمن مهمة مستقلة ومختبرة.
- عدم إضافة طبقات UseCase شكلية لا تحتوي على قواعد أو تنسيق فعلي.

### المخرجات
- حدود واضحة لقراءة البيانات وكتابتها.
- مستودعات قابلة للاختبار.
- خطة واضحة لأي تغيير ضروري في مخطط البيانات.

### بوابة النجاح
تعمل الميزات الحالية على نفس البيانات وبنفس السلوك، ولا توجد عمليات تخزين موزعة داخل الواجهة دون سبب.

---

## المرحلة 6 — توحيد الإعدادات والتفضيلات

### الهدف
جعل الإعدادات قابلة للحفظ والاختبار والاستخدام من أكثر من شاشة دون تكرار المنطق.

### المهام
- حصر كل إعداد موجود ومكان قراءته وكتابته.
- تحديد القيم الافتراضية وسلوك التوافق مع الإصدارات السابقة.
- استخدام DataStore إذا كان متوافقًا مع تصميم المشروع ولا يوجد حل قائم يؤدي الغرض بصورة سليمة.
- تعريف واجهة واضحة لقراءة الإعدادات وتحديثها.
- جعل الشاشات تستهلك حالة الإعدادات بدل نسخ القيم في متغيرات محلية طويلة العمر.
- اختبار إعادة تشغيل التطبيق واستعادة الإعدادات.
- اختبار القيم القديمة أو المفقودة أو غير الصالحة.
- عدم إضافة إعدادات جديدة أثناء نقل الإعدادات الحالية، إلا إذا كانت ضرورية ومصرحًا بها.

### المخرجات
- مصدر موحد للتفضيلات.
- اختبارات للقيم الافتراضية والحفظ والاستعادة.
- توثيق سلوك الإعدادات عند الترقية.

### بوابة النجاح
تظل الإعدادات الحالية كما هي للمستخدم، وتستمر القيم المحفوظة في العمل دون فقد بيانات أو تغييرات غير مقصودة.

## المرحلة 7 — تنظيم المكتبة وميزات المحتوى

### الهدف
فصل ميزات المكتبة عن بعضها وتقليل تأثير أي ميزة على الأخرى.

### المهام
- تنظيم عرض المكتبة والتنقل والبحث.
- فصل منطق المفضلة عن شاشة المكتبة وعن المشغل.
- تصميم قوائم التشغيل كميزة ذات نماذج وعمليات واضحة.
- تصميم المجلدات أو التجميعات وفق احتياجات المشروع الفعلية.
- تحديد قواعد التعامل مع حذف ملف أو نقله أو اختفائه بالنسبة للمفضلة والقوائم وسجل المشاهدة.
- إعادة استخدام المستودعات والعقود المشتركة بدل نسخ عمليات التخزين.
- اختبار عدم وجود فيديو أو ملف، والتحديثات المتزامنة، والبيانات القديمة.
- عدم تغيير تصميم المكتبة أثناء إعادة الهيكلة إلا إذا كانت المهمة تتضمن تغييرًا بصريًا معتمدًا.

### المخرجات
- حدود مستقلة نسبيًا لكل ميزة.
- قواعد واضحة للعلاقات بين بيانات المكتبة.
- اختبارات لتفاعلات الميزات مع بعضها.

### بوابة النجاح
تعديل منطق المفضلة لا يتطلب تغيير كود التشغيل، وتعديل منطق قوائم التشغيل لا يغيّر عرض المكتبة أو سلوكها دون سبب واضح.

## المرحلة 8 — تحسين الصور المصغرة والمهام المكلفة

### الهدف
منع العمليات المكلفة من إبطاء الواجهة أو تكرار العمل.

### المهام
- مراجعة طريقة استخراج الصور المصغرة وتخزينها المؤقت.
- تحديد مكان تنفيذ العمل الثقيل وملكية الموارد.
- منع إعادة تنفيذ العمل المكلف بلا داعٍ بسبب إعادة تركيب Compose.
- التحقق من الإلغاء عند مغادرة الشاشة أو تغيير المصدر.
- مراجعة التعامل مع الذاكرة والملفات المؤقتة والأخطاء.
- قياس الأداء قبل التحسين وبعده عند توفر أدوات القياس.
- عدم إضافة caching أو concurrency معقدين دون قياس يبرر الحاجة.

### المخرجات
- تدفق واضح لمعالجة الصور المصغرة.
- اختبارات لسلوك الإلغاء والأخطاء عند الإمكان.
- أدلة قياس لأي تحسين أداء يُدّعى.

### بوابة النجاح
لا يوجد تدهور مرئي في الأداء أو تسريب موارد، وأي تحسين مدعى به مدعوم بقياس.

## المرحلة 9 — مراجعة حدود الحزم وقرار Gradle modules

### الهدف
تقرير ما إذا كان الفصل داخل `:app` كافيًا أو أن بعض الأجزاء تحتاج وحدات بناء مستقلة.

### المهام
- مراجعة اتجاهات الاعتماد بعد اكتمال الفصل.
- التأكد من عدم وجود اعتماديات دائرية.
- تحديد الأجزاء التي يمكن اختبارها وبناؤها بصورة مستقلة.
- قياس تكلفة البناء والصيانة، لا التخمين.
- تحديد ما إذا كانت وحدة مستقلة ستفرض حدًا معماريًا مفيدًا أم ستزيد التعقيد فقط.
- إن تقرر إنشاء Gradle module، فليكن النقل محدودًا مع تحديث إعدادات البناء والاختبارات والاعتماديات.
- عدم تحويل كل حزمة إلى module.

### معايير قرار إنشاء module
ينبغي أن يحقق واحدًا أو أكثر من فوائد ملموسة، مثل:
- فرض حدود اعتماد لا يمكن ضمانها بالحزم وحدها.
- استقلال اختبار أو بناء جزء واضح.
- ملكية واضحة لمجال مستقل.
- تقليل ملموس في زمن البناء أو التعقيد.
- إعادة استخدام حقيقية خارج الوحدة الحالية.

### المخرجات
- قرار موثق لكل module مقترح.
- إما الإبقاء على `:app` منظمًا داخليًا، أو خطة وحدات محدودة ومبررة.

### بوابة النجاح
لا تُنشأ modules لمجرد أن المعمارية تبدو أكثر احترافية على الورق.

## المرحلة 10 — اختبارات شاملة ومراجعة الانحدارات

### الهدف
التحقق من سلامة التطبيق بعد اكتمال إعادة الهيكلة.

### المهام
- تشغيل جميع اختبارات الوحدة.
- تشغيل Lint.
- تشغيل الاختبارات البصرية عند توفر متطلباتها.
- تشغيل اختبارات Android instrumentation عند توفر جهاز أو Emulator.
- اختبار التشغيل والإيقاف والتبديل بين الفيديوهات واستعادة الحالة.
- اختبار الإيماءات والإعدادات والمكتبة والمفضلة والقوائم وفق الميزات الموجودة.
- اختبار تدوير الشاشة وسطح الفيديو وPiP إن كانت مدعومة.
- مراجعة تحذيرات Manifest والصلاحيات والإشعارات.
- مقارنة النتائج بخط الأساس لتحديد التحذيرات الجديدة.
- توثيق أي اختبار لم يمكن تشغيله والسبب، وعدم تحويل ذلك إلى ادعاء نجاح.

### المخرجات
- تقرير اختبار نهائي.
- قائمة بالانحدارات إن وجدت وطريقة معالجتها.
- قائمة بالقيود أو الاختبارات المؤجلة.

### بوابة النجاح
جميع الاختبارات المطلوبة والمتاحة تمر، ولا توجد انحدارات معروفة غير معالجة. الحالات التي تحتاج جهازًا فعليًا موثقة بوضوح.

## المرحلة 11 — التوثيق وقواعد التطوير المستقبلية

### الهدف
جعل المعمارية مفهومة للمطورين ووكلاء الذكاء الاصطناعي الذين سيعملون على المشروع لاحقًا.

### المهام
- إنشاء أو تحديث `ARCHITECTURE.md`.
- توثيق مسؤولية كل طبقة واتجاه الاعتماد.

- توثيق مكان إضافة ميزة جديدة من كل نوع.
- توثيق طريقة تشغيل الاختبارات ومتطلبات الاختبارات البصرية والجهاز.
- توثيق القرارات المعمارية المهمة وسببها.
- إنشاء قواعد مراجعة تمنع إعادة تجميع كل المنطق داخل شاشة واحدة.
- توضيح أن حدود الملفات تحدد بالمسؤولية لا بعدد أسطر ثابت.
- تحديث تعليمات المشروع الخاصة بوكلاء البرمجة إن وجدت.

### المخرجات
- `ARCHITECTURE.md`.
- سجلات قرارات معمارية مختصرة عند الحاجة.
- إرشادات للمساهمة والتعديل.
- قائمة تحقق لإضافة ميزة جديدة.

### بوابة النجاح
يستطيع مطور جديد تحديد المكان الصحيح لتعديل ميزة ومعرفة الاختبارات المطلوبة دون قراءة المشروع كله أولًا.

## المرحلة 12 — استئناف تطوير الميزات

لا تبدأ هذه المرحلة إلا بعد اعتماد مراحل إعادة الهيكلة الأساسية أو توثيق الاستثناءات المتبقية.

### ترتيب مقترح

1. إكمال أو مراجعة سلوك Long-Press 2x والإيماءات القابلة للضبط إذا لم يكن قد اكتمل بالفعل.
2. إكمال إعدادات DataStore والتأكد من حفظها واستعادتها.
3. تحسين عرض المكتبة بأسلوب Grid.
4. إضافة أو استكمال Favorites.
5. إضافة أو استكمال Playlists.
6. إضافة أو استكمال Folders.
7. تحسينات تجربة الاستخدام والأداء وفق نتائج فعلية.
8. توسيع CI/CD وفحوص الإصدار والتوافق مع الأجهزة.

**ملاحظة:** يجب مراجعة حالة كل ميزة في المستودع قبل جدولتها؛ لا تُنفذ ميزة موجودة بالفعل لمجرد ظهورها في هذه القائمة.

### قواعد إضافة كل ميزة مستقبلية

- تحديد نطاق الميزة ومسؤوليتها قبل كتابة الكود.
- تحديد المكونات والعقود التي ستتأثر.
- إضافة اختبارات للسلوك الجديد والحالات الحدّية.
- تجنب وضع منطق أعمال جديد في الشاشة لمجرد سهولة الوصول.
- عدم تعديل أجزاء غير مرتبطة إلا مع توضيح السبب.
- تشغيل الاختبارات المناسبة ومراجعة diff قبل اعتماد العمل.
- توثيق أي قرار معماري جديد عند تأثيره على بقية المشروع.

# 6. بوابات التحقق الموحدة لكل مرحلة

لا تُعتبر أي مرحلة منتهية لمجرد أن الوكيل نقل الملفات أو قال إن الكود أصبح أنظف.

لكل مرحلة، يجب تقديم:

1. **الهدف والنطاق:** ما الذي تغير ولماذا؟
2. **الملفات:** قائمة الملفات المضافة والمعدلة والمحذوفة.
3. **الحدود المعمارية:** ما المسؤولية التي تم فصلها؟ وما الاعتماديات التي تغيرت؟
4. **الحفاظ على السلوك:** ما الاختبارات التي تثبت ذلك؟
5. **نتائج الأوامر:** الأوامر الفعلية ومخرجاتها الأساسية.
6. **القيود:** ما الذي لم يمكن اختباره، ولماذا؟
7. **مراجعة diff:** التأكد من عدم وجود تغييرات غير مرتبطة أو حذف غير مقصود.
8. **حالة Git:** التحقق من الملفات المعدلة وغير المتتبعة.
9. **قرار المرحلة:** نجاح، أو نجاح جزئي، أو فشل مع خطة معالجة.
10. **الخطوة التالية:** لا تبدأ المرحلة التالية قبل قبول مخرجات الحالية.

يجب الفصل بين:
- فشل الاختبار بسبب خطأ في الكود.
- تعذر الاختبار بسبب الشبكة أو نقص الاعتماديات أو الجهاز.
- اختبار لم يتم تشغيله.
- اختبار نجح فعلًا.

---

# 7. استراتيجية Git والاسترجاع

- تسجيل SHA البداية قبل التنفيذ.
- عدم الكتابة فوق تغييرات موجودة أو حذف ملفات غير معروفة.
- تنفيذ كل مرحلة في diff محدود وواضح.
- الاحتفاظ بنقاط استرجاع عبر commits عند توفر الإذن المناسب.
- عدم جمع إعادة الهيكلة مع ميزة جديدة في commit واحد إلا لضرورة موثقة.
- عدم استخدام force push.
- عدم تنفيذ commit أو push دون إذن صريح إذا كانت المهمة الحالية لا تمنحه.
- قبل أي نشر، التحقق من حالة الفرع والـ remote وتعارضات العمل.
- بعد النشر المصرح به، التحقق من SHA البعيد ومحتوى الملفات المنشورة.

---

# 8. معايير قبول الخطة كاملة

تُعتبر إعادة الهيكلة ناجحة عندما:

- تظل الميزات الحالية متاحة وبالسلوك المتوقع.
- لا توجد انحدارات معروفة غير معالجة.
- تصبح مسؤوليات الشاشات والخدمات والمستودعات واضحة.
- يقل التداخل بين تشغيل الفيديو وواجهة المستخدم والبيانات.
- لا توجد اعتماديات دائرية معروفة بين الطبقات.
- تصبح المكونات الأساسية قابلة للاختبار دون الحاجة إلى تشغيل التطبيق كاملًا، حيثما كان ذلك مناسبًا.
- توجد اختبارات حماية للسلوك المهم.
- تُوثق بوضوح الاختبارات التي تتطلب جهازًا فعليًا.
- يمكن تحديد الملفات المتوقعة للتعديل عند إضافة ميزة جديدة.
- توجد وثيقة معمارية وإرشادات تساعد المطور أو وكيل الذكاء الاصطناعي.
- لا يكون التعقيد قد زاد بسبب طبقات أو modules غير ضرورية.
- تكون كل التغييرات قابلة للمراجعة والاسترجاع.

# 9. المخاطر وكيفية الحد منها

| الخطر | طريقة الحد منه |
|---|---|
| كسر سلوك قائم أثناء النقل | اختبارات قبل النقل وبعده، ونطاق صغير لكل تغيير |
| تقسيم زائد ينتج ملفات كثيرة مترابطة | فصل حسب المسؤولية والحدود، لا حسب عدد الأسطر |
| إعادة كتابة كبيرة يصعب مراجعتها | نقل تدريجي مع مراجعة diff بعد كل خطوة |
| تكرار مصادر حالة التشغيل | تحديد مصدر الحقيقة وعقد تدفق الحالة |
| مشكلات دورة حياة Android لا تظهر في JVM | اختبارات جهاز أو Emulator وتوثيق ما لم يُختبر |
| فقد بيانات أثناء تغيير التخزين | الحفاظ على المخطط والتوافق، واختبارات ترحيل عند الضرورة |
| تعقيد زائد بسبب Clean Architecture شكلية | إضافة التجريدات عند وجود حاجة عملية فقط |
| ادعاء نجاح بناء لم يُنفذ | تسجيل الأوامر والنتائج والقيود الفعلية |
| اختلاط التعديلات القديمة بإعادة الهيكلة | فحص Git قبل العمل وعزل نطاق المهمة |
| أن يعود الكود للتكدس بعد انتهاء الخطة | قواعد مراجعة وتوثيق ومراجعة حدود المسؤوليات في كل ميزة |

# 10. أول مهمة تنفيذية

ابدأ بالمرحلة 0 والمرحلة 1 فقط: **تثبيت خط الأساس والتدقيق المعماري**.

لا تنقل الملفات ولا تعِد كتابة أي جزء في هذه الخطوة. افحص المستودع الفعلي، ولا تفترض أن حالة الملفات أو الفرع أو SHA تطابق تقارير سابقة دون التحقق.

يجب أن ينتهي التدقيق بتقرير يحتوي على:

- SHA والفرع وحالة Git.
- نتائج الاختبارات الحالية وأي قيود.
- قائمة بأكبر الملفات ومسؤولياتها الفعلية.
- خريطة الاعتماديات بين الواجهة والتشغيل والبيانات.
- أبرز نقاط الاقتران والتكرار والمخاطر.
- خطة نقل مرتبة حسب المخاطر والفائدة.
- اختبارات الحماية اللازمة قبل كل عملية نقل.
- توصية مبررة بشأن البقاء داخل `:app` أو إنشاء وحدات مستقلة مستقبلًا.

بعد مراجعة هذا التقرير، يبدأ التنفيذ في مرحلة واحدة فقط، ثم تُراجع نتائجها قبل الانتقال إلى المرحلة التالية.

## القرار النهائي

**الأولوية الآن هي تحسين المعمارية، لا إضافة مزيد من الميزات.** نثبت السلوك الحالي، ونفصل المسؤوليات تدريجيًا، ونختبر كل تغيير، ثم نستأنف التطوير على أساس يمكن صيانته.

الهدف ليس أن يقرأ وكيل الذكاء الاصطناعي أقل عدد ممكن من الملفات بأي ثمن؛ الهدف أن تكون الملفات والعقود والاختبارات منظمة بحيث يعرف أين يغيّر الكود، وما الذي قد يتأثر، وكيف يثبت أن التعديل لم يكسر بقية التطبيق.
